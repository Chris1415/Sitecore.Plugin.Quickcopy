## 1. Summary

QuickCopy's Page Context Panel prefetches three URL slots (copy / live / share) on every page the marketer lands on. Add a short **debounce on `pageInfo.id` change (~200 ms)** so that rapid page-to-page navigation no longer fires the prefetch trio for every transient page — only the page the user actually settles on — keeping the panel responsive and cutting wasted API calls, with no change to the existing per-id cache.

### Problem (one short paragraph)

The panel fires three API calls per visited page even when the user never copies a URL. For a marketer tabbing quickly through many pages, that is a real, repeated cost. ADR-0006 named a ~200 ms debounce on `pageInfo.id` change as a "low-risk follow-up" deliberately deferred from v0.1.

### Goal (one short paragraph)

Debounce the prefetch trio on `pageInfo.id` change so rapid navigation issues far fewer calls, while a settled page still resolves all three slots and cached ids (back/forward) still resolve from cache.

### Non-negotiables (bullets)

- The existing per-id cache stays intact — back/forward to an already-fetched id must NOT trigger a new network call.
- No change to cache invalidation (ADR-0007 version-keyed behavior is untouched).
- A settled page still resolves copy / live / share correctly (no dropped fetches).

### In scope / out of scope (very short)

- **In scope:** a single ~200 ms debounce on `pageInfo.id` change, applied before the prefetch trio fires.
- **Out of scope:** changing the cache strategy, adding a `/live`-slot TTL (that is TASK-002 / FRD-002), or altering what the three slots fetch.

### Acceptance criteria (the definition of done — 3–7 bullets, each independently verifiable)

- Rapidly switching across N pages within the debounce window issues far fewer than 3×N prefetch calls (only the settled page's trio fires).
- Landing and settling on a page resolves all three slots (copy / live / share) exactly as before.
- Navigating back/forward to a previously fetched id resolves from cache with no new network call.
- The debounce interval is a single named constant (default ~200 ms) so it can be tuned without hunting.
- The existing test suite stays green, and a new test asserts that rapid `pageInfo.id` changes collapse to one settled fetch.

### Key constraints & assumptions

- Trigger signal is the `pageInfo.id` change (per ADR-0006); the prefetch is assumed to currently fire from an effect/hook keyed on that id — the Developer confirms the exact call site.
- This is an implementation refinement consistent with ADR-0006 / ADR-0007; no new ADR.

## 2. Problem / motivation

Today the panel composes live URLs via parallel prefetch on every page context change (ADR-0006). The marketer who tabs through many pages quickly pays three API calls per page even though most pages are passed over without a copy. ADR-0006 explicitly recorded the mitigation — "a debounce on `pageInfo.id` change (e.g. 200 ms) is a low-risk follow-up — but v0.1 ships without it" — and noted the per-id cache already covers back/forward navigation. This FRD picks up that deferred follow-up.

## 3. Acceptance criteria (authoritative)

1. **Fewer calls under rapid navigation.** Programmatically driving N quick `pageInfo.id` changes within the debounce window results in a single settled prefetch trio (≪ 3×N calls). Verified by a unit/integration test that counts fetch invocations.
2. **Settled page still correct.** After the debounce settles, copy / live / share resolve with the same values they do today (no dropped or stale slot).
3. **Cache preserved.** Back/forward to an already-fetched id resolves from the per-id cache with zero new network calls (ADR-0006 cache behavior unchanged).
4. **Tunable constant.** The debounce delay is a single named constant (default ~200 ms).
5. **Suite green + new test.** All existing tests pass; a new test asserts rapid id changes collapse to one settled fetch.

## 4. Scope

### In scope
- A debounce (~200 ms) on `pageInfo.id` change before the prefetch trio.
- One new test for the debounce behavior.

### Out of scope
- `/live`-slot TTL fallback (tracked separately as TASK-002).
- Any change to cache invalidation, slot composition, or the share-link formats.

## 4a. Execution tranches (probe-first)

No load-bearing external/SDK/tenant assumption here — the only unknown is the prefetch call site, which is confirmed by reading the code, not by a `/probe`. Single build tranche.

- **Tranche 1:** Add the debounced trigger around the existing prefetch, with the count-asserting test.

## 5. Constraints & assumptions

- **Decision:** debounce keyed on `pageInfo.id` change (ADR-0006).
- **Assumption:** the prefetch currently fires from an effect/hook on `pageInfo.id`; Developer confirms the exact location before wiring the debounce.

## 6. Technical considerations

No ADR-worthy decision — this is an implementation refinement consistent with ADR-0006 (parallel prefetch) and ADR-0007 (version-keyed cache). Straight to task breakdown; `/architect` skipped.

## 7. Risks

- A too-long debounce makes the panel feel laggy when the user settles. Mitigation: default ~200 ms and keep it a single tunable constant.

## 8. Open questions

- Exact debounce value (200 ms is the ADR-0006 suggestion; tune during smoke if it feels slow). Not blocking.
